Cline Pass 上游控制台

本地代理 + 观测面板 —— 账号池固定按请求轮询（无会话粘性）；订阅模型可选只使用命中官方渠道的 key（如 deepseek-v4.1-flash 跳过非官方 key，并定时复检是否恢复）
尚未配置上游 API Key：在下方「账号管理」添加你的 Cline Pass 账号（sk_ 开头的 key）并保存即可开始使用；也可通过 config.json 的 accounts 或环境变量 CLINE_PASS_KEY 提供。
实测原理：为什么能钉住上游（点开看细节）
① 上游可枚举、可观测：订阅模型响应元数据里带背后真正的模型 ID、可用上游列表与本次实际命中的上游； 「探测」按钮还会用一次零 token 消耗的假上游请求让网关报出精确的可用上游清单（直连→OpenRouter，规划器→Vercel AI Gateway）。
② 两类管道都能精确钉住上游（已实测 finalProvider 随之改变）： 直连管道（OpenRouter）用顶层 provider.only / order； 规划器管道（Vercel AI Gateway）必须用 providerOptions.gateway.only / order—— Cline 会丢弃顶层 provider 简写里的 only/order，但会透传 providerOptions.gateway。 两类管道还都支持 sort（最低成本 / 最快首字 / 最高吞吐）。
⚠ 2026-09 起规划器可能静默失效：Cline 已多次变更规划器，部分模型的 providerOptions.gateway.only 会被整个忽略（连非法渠道 __probe__ 都不再被路由层拒绝）。 控制台会自动检测并在顶部弹出钉住失效告警，失效时「校验」不再给假绿，而是标为未判定。直连管道（顶层 provider.only）目前不受影响。
③ 目录模型 :free 变体：属于直连管道，可精确钉住。
④ 多上游优先级 + 故障转移：勾选多个上游即按勾选顺序逐个尝试——第一个异常（报错/网络失败/超时）自动顺切下一个，全部失败才把错误透传给客户端；「排除」的上游永不被使用（自动模式下会向网关注入排除偏好）。流式请求在首包（SSE 开始）前同样可切换，SSE 开始后透传不可重试。

订阅模型（cline-pass/*）

怎么配？三种路由策略的区别（点开）
⚡ 自动不指定渠道，网关自己挑。只有「排除」生效（换算成白名单注入）。适合：对渠道没要求，只要能用。
📌 只用选中的只允许选中的渠道（only=[当前]）。选 1 个 = 死钉它，失败直接报错；选多个 = 按顺序逐个死钉尝试，前一个报错/超时才切下一个，全失败才报错。适合：必须走指定渠道，比如官方 deepseek。
🔀 优先选中的选中的排在前面（order=[当前, 其余选中]），一次尝试内网关也可以自己换渠道，排除项仍不会被用。适合：有偏好但更看可用性。
排序偏好让网关按最低成本 / 最快首字 / 最高吞吐给渠道排序。只在「自动」「优先选中的」下有意义 —— 严格只允许一个渠道，没有可排序空间。

按账号探测上游（同一模型在各账号下实际命中的供应商）

不同账号的可用凭证池可能不同，导致同一模型被路由到不同上游供应商（例如官方 deepseek vs 第三方/私有渠道）。 这里逐一探测每个账号实际命中的上游；在模型行勾选「仅使用命中官方渠道的 key」后，非官方 key 会自动从该模型的轮询里跳过， 并在轮询到它时/定时复检它是否已恢复为官方渠道。
